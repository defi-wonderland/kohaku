New on the core entry: `orderVerdict(record, selection, now)`, the gathering's ordering verdict, which `order` and `RecoveryClient.complete` both read, so a completion judges the record once. It returns `{ outcome: 'ordered', proofs }`, the proofs strictly increasing by place (the selection where one is given, otherwise the preferred satisfying set), or `{ outcome: 'refused', reason, findings }`: `window-passed` with the whole window result (errors and warnings, such as `request.moment-skew`), or `rule-unsatisfied` with the rule's findings (`proof.place-out-of-range`, `request.rule-unsatisfied`). It throws a `TypeError` on an unread record and a `RangeError` where the selection names a place no reply fills, as `order` does. New records `OrderVerdict` and `OrderRefusal`; new constants `GATHERING_ORDER_REFUSALS` (`window-passed`, `rule-unsatisfied`) and `GATHERING_ORDER_REFUSAL_MESSAGES`, the frozen map from each reason to the message `order` throws as a `RangeError` and `complete` as a `KitRefusalError` (`GATHERING_WINDOW_PASSED_MESSAGE`, `GATHERING_RULE_UNSATISFIED_MESSAGE`). `ruleCountFindings` now takes any `Pick<CheckedRequest, 'body' | 'proofs'>`; its findings are unchanged.

`complete` no longer runs the request shape guard over its candidate submission, so a hand-edited record with a malformed `account`, `action`, `payload`, `order` or reply proof member is no longer refused with a `TypeError` at `complete`; `prepareStartAttempt` and `prepareCancelByProofs` refuse it before any read, and `addApproverReply` guards replies at filing.

New: `SetupDescription.action`, of the new type `DescribedAction`, names the action a setup commits as the party that holds the account's authority once armed: its `address`, its own `actionInfo()` answer as `info` (name, version, the ERC-165 probe; self-attested, unanswered where that read failed), whether it is the descriptor's own action (`shipped`), whether the descriptor's audited list names it (`audited`), and its `supportsAccount` answer, absent where the account holds no code yet. `describeSetup` makes no new read for it, and refuses with a `TypeError` a context whose `action.actionInfo` is not an object or whose `action.supportsAccount` or `action.accountHoldsCode` is not a boolean.

`order` and `complete` keep their signatures and thrown types; these are additions only. One more case changes under `order`: a hand-built record that fills a place at or past the body's credential count, which `fileReply` never produces, now throws the rule `RangeError` (the verdict raises `proof.place-out-of-range`) where `order` used to return its proofs; `complete` already refused it. A `SetupDescription` built by hand (an integrator's double) gains the required member `action`.
