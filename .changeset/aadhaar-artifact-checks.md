The default Aadhaar stack checks the bucket's code files and reports a failed download as `device-unavailable`. Where the artifacts' `wasmURL` and `vkeyURL` are the SDK's own bucket files, as in `METHOD_AADHAAR_BUCKET_CHUNKED` (the default) and `METHOD_AADHAAR_BUCKET_SERVER`, the installed stack fetches both once per load, before the peer's `init`, compares their sha256 with the new `METHOD_AADHAAR_BUCKET_SHA256` (`wasm`, `zkey` and `vkey` as `0x` lower hex) and hands them to the peer as object URLs. The zkey URL is unchanged and the zkey is not checked; its hash is for a caller holding a whole copy of its own. A failed fetch or a mismatch rejects the load with `AadhaarStackUnavailable` and the new message `METHOD_AADHAAR_ARTIFACT_HASH_MESSAGE`. That reads `device-unavailable`, and the load is retried on the next call. Integrator URLs are neither fetched nor changed. The stack also records each progress state the peer reports before passing it to the page unchanged. A proof that rejects while the last state is a download state (the new `METHOD_AADHAAR_DOWNLOAD_STATES`, `fetching-wasm` and `fetching-zkey`) rejects with `AadhaarStackUnavailable` and the new message `METHOD_AADHAAR_STACK_DOWNLOAD_MESSAGE`, which reads `device-unavailable`. A rejection with no state, or at or after `proving`, reads `material-rejected` as before. Under `chunked` the peer drops a zkey piece's download error, so a failed or corrupt piece still reads `material-rejected` and stays in the browser's storage under its file name until the site's data is cleared. The chunked source that last wrote a name is the one every chunked proof on the page reads. The JSDoc of `METHOD_AADHAAR_BUCKET_CHUNKED` and `AnonAadhaarMethodOptions.artifacts` says so. No closed set or record changes.

Compatibility: a download that fails under the installed stack's `server` mode, or the wasm download under `chunked`, now reads `device-unavailable` instead of `material-rejected`. Over the bucket files, the default stack now fetches the 10 MB wasm and the vkey itself, once per load, and the peer reads them from memory instead of from the bucket on every proof. That uses `fetch`, `Blob` and `URL.createObjectURL`, present in browsers and in Node 22 and later. A bucket file that changes or fails to download stops proving with `device-unavailable` until it matches again. What a consumer installs, the bucket records' values and the lazy import of `@anon-aadhaar/core` are unchanged.
